# UNIMOC GUI plan (cypilot)

Status: **plan** (2026-10-23), decisions of the same day in section 2.
Nothing is built. The GUI and its CLI live in **their own repository**; this
file plans both sides until that repository exists. After that, the GUI side
moves there and this file keeps only the contract with the firmware (sections
5.1, 6, 7.1 and 9). It replaces the GUI items of
`docs/software_in_loop_plan.md` (Phase 5) and of `TODO.md` (SIL P3).

## 1. Goal

cymon is the generic Cyphal debug tool: any register, any subject, any
service, by hand. UNIMOC also needs an operator tool for the everyday jobs on
one to many UNIMOC nodes, where the user does not write registers or publish
messages by hand:

- find all nodes of a bus and show at a glance what state each one is in
  (engaged, tripped, E-stop latched, limp-home, settings pending, bus-off);
- read, edit, compare, store and restore the settings of every node, with the
  register list scanned from the node, not taken from a fixed list;
- enable and disable one drive, a chosen set or all drives, with setpoints,
  and stop everything with one key;
- recover a node from an emergency stop, a trip or a fault by guided steps;
- plot live values of several nodes in one time base, and take triggered
  scope shots (cymon) on several nodes at once;
- work the same way against the `native_sim` instances and the real bus.

Scope of nodes: 1 to at least 4 wheel drives first, then the vehicle dynamics
controller (VDC), the BMS controller (`docs/system_plan.md`) and the e-bike
drive of PR #29 (`docs/ebike_plan.md` on that branch). Any other Cyphal node
still shows up with the generic functions (heartbeat, registers, log,
subjects).

Platforms: Linux and Windows. Against the simulation the GUI runs on Linux
only; on a Windows machine the simulation and the GUI both run in WSL2
(section 10). Windows itself works with real CAN adapters only.

Not a goal: the GUI is no safety device. The hard-wired E-stop loop and the
mechanical brake stay the safety path (`docs/system_plan.md`, section 7). The
GUI does not replace cymon for protocol work, and it does not flash firmware
until the Cyphal firmware update exists (`TODO.md`).

## 2. Decisions

Decided 2026-10-23:

| Topic | Decision | Consequence |
|---|---|---|
| Place | GUI (`cypilot`) and CLI (`cypilot-ctl`) in **one separate repository**, **`Tecnologic/cypilot`** (name decided 2026-10-24; Cyphal + pilot, the operating counterpart of cymon) | Own release cycle and CI; the firmware repository stays Zephyr only. The contract between both is the DSDL, the registers, the vendor status bits and the register description file. |
| Tests | The separate repository uses **plain pytest**, also for logic tests without a simulation; the `AGENTS.md` rule "tests are ztest under twister" applies to this repository only | Its integration tests start the released `native_sim` binary (section 11). |
| Scope | **Reuse the capture client of the cymon host tool** (<https://github.com/Tecnologic/cymon>) | The GUI depends on the cymon package. If cymon does not offer its client as an importable API, that is a change in cymon, not a copy in the GUI (section 8.2). |
| Vendor status bits | Bits 4 to 7 as proposed (section 6) | Firmware change in this repository. |
| Register descriptions | A description file, **owned and generated by the firmware** of this repository, served by the node (section 5.1) | The GUI repository has no copy; it only reads the file. |
| Readiness | **Per node** (section 7.1) | Firmware change of the readiness default in this repository; the VDC arms each drive. |
| Stack | Python 3.11+, pycyphal, PySide6 (Qt 6), pyqtgraph, qasync, cymon (host) | Same stack as the existing pycyphal tests; pycyphal compiles DSDL at run time. |
| Structure | A **core** without Qt (bus, discovery, registers, control, recorder, scope), the CLI and the Qt UI on the same core | Quick jobs from the shell and scripts, headless tests, no protocol logic in the UI. |
| Threads | All Cyphal I/O on one asyncio loop in a bus thread; the UI only sends commands and receives snapshots | The UI never blocks the bus and a busy bus never freezes the UI. |
| Register list | Always scanned; no register name is hard-coded except the standard `uavcan.*` ones and the few the control functions need (section 5) | Firmware changes appear without a GUI change. |
| Node functions | **Capabilities** found by discovery (ports, `.type` registers, register prefixes), not by node type | A drive with or without the cart registers, the e-bike and an unknown node all get what they support. |

### 2.1 License (proposal)

The firmware stays GPL-3.0-or-later. For the GUI repository: **Apache-2.0**.

- It matches cymon-lib (Apache-2.0), which the GUI reuses on the host side;
  pycyphal and pyqtgraph are MIT, PySide6 is LGPL-3.0 (used as an installed
  Python package; a PyInstaller bundle ships Qt as separate, replaceable
  libraries, so no one-file bundle).
- Apache-2.0 against MIT: both allow any use; Apache-2.0 adds an explicit
  patent grant and asks for notices of changes. MIT is shorter. Either works;
  Apache-2.0 keeps the two host-side projects on one license.
- For mostly AI-written code the copyright position is unclear in several
  jurisdictions. A permissive license makes that question matter little: users
  get the same rights either way. (This is no legal advice.)
- **The DSDL needs a decision too:** the files in `dsdl/unimoc/` carry
  `SPDX-License-Identifier: GPL-3.0-or-later`, and the GUI loads and compiles
  them. Proposal: relicense `dsdl/unimoc/` to Apache-2.0 (or MIT, like the
  OpenCyphal public regulated data types), so any tool, also a closed one, can
  speak the UNIMOC protocol. This needs the consent of every contributor to
  those files; today that is the repository owner.

## 4. Discovery and the node model

Every node that publishes a heartbeat becomes a row. For each new node, or
one whose uptime went backwards (restart), the core runs:

1. `uavcan.node.GetInfo`: name, software and hardware version, unique ID,
   software CRC.
2. `uavcan.node.port.List` (published by the node every 10 s, also kept from
   the bus): subjects published and subscribed, services served.
3. Register scan (section 5) in the background, low priority, and the
   register description file when served (section 5.1).
4. Port types: the `uavcan.pub.*.type` and `uavcan.sub.*.type` registers name
   the DSDL type of each port-ID (`unimoc.drive.Telemetry.0.1` on 212). With
   them every published subject of the node can be decoded and offered for
   plotting without a list in the tool. A port without a `.type` register
   shows as "unknown type"; the user may assign one, saved per node name.
5. Capabilities from what was found:

| Capability | Found by | Enables |
|---|---|---|
| Registers | `uavcan.register.List` served | Register editor, profiles |
| Commands | `uavcan.node.ExecuteCommand` served | Restart, store, factory reset, E-stop |
| Armable drive | register `uavcan.sub.readiness.id` enabled | Enable and disable |
| Setpoints | `uavcan.sub.{current,torque,speed,position,servo}_setpoint.id` enabled | Setpoint panel with the modes found |
| Cart drive | `uavcan.sub.wheel_command.id`, publishes `unimoc.cart.DriveStatus` | Wheel index, cart status, limp-home display |
| Scope | the five `uavcan.srv.cymon_*.id` registers enabled and served | Scope, multi-node capture |
| Simulation | registers `unimoc.sim.*` | Pause, advance, reset, virtual clock |
| Local control (e-bike, PR #29) | vendor status bit 7 (section 6) | No engage button: the drive engages by itself; STANDBY and SLEEP stay |
| VDC, BMS | publishes `unimoc.cart.WheelCommand` or `unimoc.cart.BatteryStatus` | Cart overview, battery panel (when these nodes exist) |
| Log | publishes `uavcan.diagnostic.Record` | Log view with node filter |

The nodes show in a table and as a cart sketch when cart drives exist (wheel
index from `unimoc.cart.wheel`). Users can give a node a label (saved by unique
ID), so "FL drive" stays "FL drive" after a node-ID change.

## 5. Registers

- **Scan:** `List` with index 0, 1, ... until the empty name; then `Access`
  with an empty value to read each one's value, type, `mutable` and
  `persistent` flags. Names are shown as a tree on their dots
  (`unimoc.motor.limits.i_max`). About 130 registers per drive: one `List` and
  one `Access` each, at low priority, in about a second per node on a free bus.
- **Edit:** the editor follows the value type (`real32[1]` number, `natural8`
  integer or enum, `bit` check box, `string` text, arrays as lists), with the
  unit, range and help of the description file when it is there. A write is
  checked against the answer: the drive answers a rejected write with the
  unchanged value (README, "Registers"), so the GUI shows "rejected" instead
  of a silent no-op. After the write the GUI reads vendor status bit 6
  (settings pending) and shows "waits for disengage".
- **Store:** `ExecuteCommand STORE_PERSISTENT_STATES` per node or for all
  changed nodes; the GUI shows the `BAD_STATE` refusal while the power stage is
  enabled with its reason.
- **Profiles:** save all persistent registers of a node to JSON (with node
  name, software version and date), load it into the same or another node
  (diff first, then write, then verify, then store), compare two nodes or a
  node with a file. Copying one drive's settings to the other three drives is
  the main use. Port-ID and node-ID registers are skipped on load unless asked,
  so a profile does not create a port collision or a duplicate node-ID.
- **Search and filter:** by name, only changed, only non-default, only
  mutable.
- **Restart-needed hint:** port-ID and node-ID changes take effect after a
  restart; the GUI offers the restart after storing.

### 5.1 Register description file (owned by this repository)

A scan gives names, types and values, but no unit, range, default or help
text. The firmware owns that knowledge, so the firmware owns the file:

- **Source:** `ForEachRegister()` (`lib/settings/settings_registers.hpp`) and
  the register providers of the applications get a unit, the limits of the
  validation, the default, a live-tunable flag and one line of help per
  register, next to the register itself. Each application (drive, VDC, BMS,
  e-bike) describes its own registers in the same way.
- **Generator:** the build writes `registers.json` (schema version, firmware
  version and VCS revision, one entry per register). A twister test checks
  that every register on the bus has an entry and the other way round.
- **Delivery, step 1:** the CI attaches `registers.json` to the firmware
  artifacts and the release, next to `unimoc-bcc-*.elf` and
  `unimoc-native_sim-*.tar.gz`. The GUI picks it by the software version and
  VCS revision of `GetInfo`, from a local folder or the release.
- **Delivery, step 2:** the node serves it compressed through
  `uavcan.file.Read` (path `unimoc/registers.json.gz`, a few KB in flash) once
  the Cyphal file service exists (it comes with the firmware update). Then the
  description always matches the running firmware.
- **The schema** is documented in this repository (`docs/settings_plan.md`)
  and versioned; the GUI accepts the versions it knows and falls back to the
  bare scan otherwise.

## 6. Status

The status line of each node is built from what the node publishes, in this
order of freshness:

| Source | Rate | Content |
|---|---|---|
| Heartbeat | 1 Hz | Health, mode, uptime, vendor status (below) |
| `unimoc.cart.DriveStatus` | 50 Hz | Engaged, power stage, limp-home, regen derated, overcurrent and overvoltage trips, temperatures, DC link |
| `unimoc.drive.Telemetry` | 20 Hz | Engaged, power stage, overcurrent trip, currents, voltages, speed, DC link |
| Registers, polled at about 1 Hz while the node is selected | — | `unimoc.can.bus_off_count` |
| `uavcan.diagnostic.Record` | event | Last warning or error in the row, full text in the log |

Vendor status code of the heartbeat (decided 2026-10-23; bits 0 to 3 exist
in `DriveNode::UpdateStatus()`, bits 4 to 7 are new):

| Bits | Meaning |
|---|---|
| 0 to 2 | Power stage state: 0 disabled, 1 enabled, 2 fault, 3 blocked (as in `unimoc.drive.Telemetry`) |
| 3 | Engaged |
| 4 | Trip latched (overcurrent or overvoltage), cleared by `STANDBY` |
| 5 | Emergency stop latched, cleared by a restart |
| 6 | Settings pending (`unimoc.settings.pending`) |
| 7 | Local control: the node engages by itself (e-bike, PR #29) |

With them the heartbeat alone gives the full status of any UNIMOC node, also
without `DriveStatus` or `Telemetry` enabled. A non-drive application (VDC,
BMS) that has no power stage sets bits 0 to 4 to zero and keeps 5 to 7 with the
same meaning where they apply.

States shown as colored chips: **Offline** (no heartbeat for 3 s),
**Disabled**, **Engaged**, **Blocked** (external enable missing, the E-stop
loop is open), **Tripped**, **Fault**, **E-stop latched**, **Limp-home**,
**Settings pending**, **Local control**, plus health and mode.

## 7. Control

### 7.1 Readiness per node (firmware change in this repository)

Decided 2026-10-23: every drive has its **own readiness subject**, so the GUI
(and the VDC) can enable each drive alone.

- **Default:** `uavcan.sub.readiness.id` follows the node-ID,
  `kSubReadinessBase + node-ID` (proposed base 1024: 1024 to 1151 for the CAN
  node-IDs 0 to 127, clear of the IDs in use today), as long as the register
  was not written. Reading the register gives the effective ID. Writing an ID
  fixes it; a factory reset returns to "follows the node-ID". A node-ID change
  moves the readiness subject with it after the restart, like every port.
- **Collision check:** the existing check of the port registers includes the
  derived ID.
- **GUI:** "Enable" publishes `ENGAGED` on the subject of each selected drive,
  "Enable all" on all of them; readiness costs one frame per drive and period
  (about 4 frames at 20 Hz for four drives).
- **Cart:** the VDC arms each drive on its subject. The README, the system
  plan (section 6.2) and `sim_client.py` (`PORT_READINESS = 106`) change with
  it.
- **Setpoints** stay on shared subjects: only an engaged drive applies them,
  so per-node readiness already allows "this drive runs, the others are off".
  Different setpoints for several engaged drives at once (not the cart, which
  has one torque per wheel in `WheelCommand`) would need the same scheme for
  the setpoint subjects; open point in section 13.
- **No two masters:** if any other node publishes on a drive's readiness or
  setpoint subject (seen in its `port.List`), the GUI shows it and does not
  publish there; it still offers STANDBY through an override with a
  confirmation.

### 7.2 Keep-alive and dead man

The drive disengages when readiness or setpoints are not refreshed within
`unimoc.control.command_timeout` (0.5 s). The GUI publishes readiness and
setpoints of every enabled drive at 20 Hz from the bus thread. The UI thread
feeds a watchdog of the bus thread: if the UI stalls for longer than 0.3 s,
the bus thread stops the readiness publications, and the drives disengage by
their own timeout. Closing the GUI or losing the adapter has the same effect.

### 7.3 Enable, disable, stop

| Action | What the GUI does |
|---|---|
| Enable (selected drives or all) | Checks the preconditions (not blocked, nothing latched, no local control, no foreign publisher, setpoint zero), then publishes `ENGAGED` on each drive's subject and keeps it alive; shows the engaged bit coming back from each drive, or a timeout with the reason |
| Disable | Ramps the setpoint to zero (configurable ramp), then publishes `STANDBY` for a second, then stops publishing |
| Stop all (Esc key, always visible) | Publishes `SLEEP` on every readiness subject it knows and zero setpoints, at once, no ramp |
| Emergency stop (button with confirmation, or Shift+Esc) | `ExecuteCommand EMERGENCY_STOP` (65531) to every node that serves it; latched until a restart |

### 7.4 Setpoints

One panel for the selected drives, with the modes they subscribe (current d/q,
torque, speed, position, UDRAL servo). Inputs: number field, slider with
limits from the node's registers (`unimoc.motor.limits.i_max`, the speed range),
a ramp, and a step or a square wave of chosen amplitude and period for
tuning. The setpoint goes to zero on disable and on stop.

Cart: a "cart" panel publishes `unimoc.cart.WheelCommand` with one torque per
wheel (or one for all) and `unimoc.cart.PedalState` for limp-home tests, only
while no VDC or pedal unit is on the bus.

### 7.5 Recovery

A "Recover" button on a node that is not ready runs the procedure that fits
its state, step by step, with each step's result shown:

| State | Procedure |
|---|---|
| Tripped (bit 4) or fault | Stop the keep-alive of the drive, publish `STANDBY` (acknowledges the latched trip), wait for bit 4 and the fault state to clear, then "ready to enable" |
| E-stop latched (bit 5) | Confirm, `ExecuteCommand RESTART`, wait for the heartbeat with a reset uptime, rescan the node, check that nothing is latched |
| Blocked | Cannot be cleared from the bus: "external enable missing, check the E-stop loop"; the chip clears by itself when the enable returns |
| Bus-off counted | Shows the count and the time of the last one; nothing to do on the node, it rejoins by itself |
| Offline | Shows the last known state and waits; offers a restart when the node comes back with an error |

"Recover all" runs the procedure on every node of a selection, in parallel,
and lists what is still not ready.

### 7.6 Simulation

When a node has the `unimoc.sim.*` registers: pause, run, advance N cycles,
reset, the virtual cycle count and period, and the simulation settings
(load torque, DC-link voltage) as a panel. Several simulated nodes are paused
and advanced together (one after the other; the cluster has no shared clock
yet, `TODO.md`, SIL P2).

## 8. Signals, plots, scope

### 8.1 Live plots

- Every decoded subject of every node is a source of named channels
  (`FL drive / Telemetry / i_q`), with the arrival time of the transfer as the
  time stamp (pycyphal reception time; one clock for all nodes).
- Plot windows with any number of channels from any nodes, shared or own Y
  axes, pause, cursor, auto scale. pyqtgraph draws the decimated view;
  the recorder keeps everything.
- The recorder keeps the last N minutes of all subscribed channels and of all
  register writes and commands the GUI sent (as markers). Export to CSV (one
  file per subject, wide format) and JSON (metadata: nodes, versions, register
  snapshot); replay of an export in the same plot windows.
- Rates are what the nodes publish (telemetry 20 Hz, drive status 50 Hz). The
  GUI can raise `unimoc.telemetry.rate` for a session and restores it.

### 8.2 Triggered scope shots (cymon)

For control-cycle resolution (16 kHz) the scope uses the cymon services of the
nodes (`docs/cymon_integration_plan.md`, `lib/cymon/dsdl/cymon`) through the
**capture client of the cymon host tool**. The GUI adds the multi-node part:

1. Per node, through the cymon client: the variables (`GetVariableList`), the
   limits and the tick period (`GetBufferInfo`), with the service IDs read
   from the node's `uavcan.srv.cymon_*.id` registers.
2. The user picks channels per node (at most `max_channels`, 8), the length,
   the sample period and the pre-trigger part, and one trigger: a variable of
   one node with rising, falling, hysteresis or immediate, and a level.
3. `SetupCapture` on every node, then `ArmTrigger`: the trigger node with the
   trigger condition; the other nodes armed so that the trigger node's
   `cymon.TriggerEvent` triggers them.
4. Poll until `COMPLETE`, then read the frames at low priority, node after
   node, with a progress bar.
5. Show all nodes in one plot, each aligned on its own trigger sample, and
   export like the recorder.

Multi-node trigger: the nodes need the shared trigger subject
(`uavcan.pub.cymon_trigger.id` and `uavcan.sub.cymon_trigger.id` on one
subject-ID on every node, decided 2026-10-22). The GUI checks it and offers to
set it (store and restart, it is a port). The trigger reaches the other nodes
through the Cyphal thread (woken at least every 1 ms) and the bus, so their
trigger sample is late by about 1 to 2 ms; the GUI shows this as an
uncertainty band, and the value is measured in the simulation (section 11).
For a tighter alignment every node can trigger on its own copy of a shared
event (for example a setpoint step), which the GUI offers as "trigger each
node on its own signal".

Bus time: a full 8 by 1024 capture is about 0.4 s per node at 1 Mbit/s with
CAN FD frames (cymon plan); over classic slcan with 8-byte frames about eight
times as long.

**Needed from cymon (host):** the capture client as an importable Python API
without its web server (session on a given pycyphal node, service IDs as
parameters, async calls, the capture as arrays with the sample period), and
a released package version the GUI can pin. Multi-node orchestration stays in
the GUI unless cymon wants it too.

## 9. Firmware support (this repository)

Each its own PR with ztest and pytest coverage:

1. **Vendor status bits 4 to 7** (section 6). README, "Commands".
2. **Readiness per node** (section 7.1): derived default, register reads the
   effective ID, collision check, README, system plan section 6.2,
   `tests/integration/cyphal_sim`.
3. **GetInfo name convention** per application: `org.tecnologic.unimoc.drive`,
   `.vdc`, `.bms`, `.ebike`, `.sim` suffix for the simulation. Shown in the
   GUI; the capabilities still come from discovery.
4. **`.type` registers** for every port of every application (the drive has
   them), so the GUI can decode every subject.
5. **Register description file** (section 5.1): metadata next to the
   registers, the generator, the twister check, the CI and release asset; the
   served file after the Cyphal file service.
6. **`scripts/sim_cluster.sh`**: starts N `native_sim` drives on `vcan0` with
   their own flash files, node-IDs (10, 11, ...) and wheel indices; the
   multi-node simulation of `TODO.md` ("Next") is the precondition. The GUI
   repository's tests use it from the release.
7. **License of `dsdl/unimoc/`** (section 2.1), if accepted.

## 10. Transports and platforms

| Transport | Linux (also in WSL2) | Windows | Use |
|---|---|---|---|
| SocketCAN `vcan0` (CAN FD, MTU 64) | yes | — | Simulation cluster |
| SocketCAN `can0` (CAN FD adapter with a kernel driver, also CANable 2.0 candleLight) | yes | — | Bench and cart |
| slcan, serial port (CANable slcan firmware) | `/dev/ttyACM0` | `COM5` | Bench, classic CAN only (pycyphal with slcan) |
| slcan, simulation pseudo terminal | `/dev/pts/N` | — | Single simulated node (one tool per pty) |
| python-can `pcan`, `gs_usb`, `kvaser`, ... | yes | yes | CAN FD adapters on Windows (PCAN-USB FD has CAN FD under python-can) |
| Cyphal/UDP | later | later | When the simulation or the cart offers it |

- **Simulation:** `native_sim` runs on Linux. On a Windows machine the
  simulation and the GUI both run in WSL2, the GUI window shown by WSLg. The
  Windows GUI does not connect to a simulation (no bridge between Windows and
  WSL2).
- **Windows:** real adapters only (python-can backends, slcan on a COM port).
  USB adapters inside WSL2 need usbipd-win and a kernel driver; not planned.
- The connection dialog lists the interfaces it finds (SocketCAN links, serial
  ports) and remembers the last ones. Settings: local node-ID (default 127, the
  tools' ID in this repository; a second tool on the bus needs another), CAN FD
  or classic MTU, bit rates for the adapters that need them.
- Packages: `pip install` (or `pipx`) first; a PyInstaller bundle for Windows
  later (Qt as separate libraries, section 2.1).
- WSL2: `vcan` in the WSL2 kernel is unverified (`TODO.md`, "Next"); without
  it the GUI in WSL2 uses the slcan pseudo terminals of a single simulated
  node.

## 11. Tests (GUI repository)

- **Unit tests** (pytest, no bus): register value conversion, profile diff and
  load order, status decoding of the vendor bits, the recovery state machines
  and the keep-alive watchdog against a fake bus.
- **Simulation tests** (pytest, Linux): CI downloads `unimoc-native_sim-*.tar.gz`
  (and `registers.json`) of the pinned `unimoc` release, starts it and
  connects over slcan, later over `vcan0` with `scripts/sim_cluster.sh`.
  Covered: discovery, the register scan against the description file, write,
  reject, store, profile round trip, enable and disable with the engaged bit,
  keep-alive timeout, stop all, the recovery procedures (trip, E-stop and
  restart), the simulation panel, a cymon capture with an immediate and a level
  trigger.
- **Qt smoke test:** with `QT_QPA_PLATFORM=offscreen`: the main window opens,
  connects, shows the node, a plot gets samples.
- **Multi-node:** with four drives on `vcan0`: enable one and all, the
  per-node readiness, multi-node capture and its trigger delay.
- **Windows CI:** unit tests and the Qt smoke test without a bus.
- **Compatibility:** CI of the GUI repository also runs against the newest
  `unimoc` release, so a protocol change shows up before the pin moves.
- Formatting and linting with ruff and a type check (mypy or pyright), pinned.

This repository keeps testing its own bus interface with
`tests/integration/cyphal_sim` under twister; nothing of the GUI enters its
CI.
